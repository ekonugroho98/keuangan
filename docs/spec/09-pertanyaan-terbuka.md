# 09 — Pertanyaan Terbuka dan Asumsi Sementara

Setiap item punya **asumsi yang dipakai spec saat ini** sehingga implementasi tidak pernah berhenti menunggu. Kalau jawaban pemilik produk berbeda, ubah spec terkait dengan catatan riwayat perubahan (lihat `08` §"Cara melanjutkan").

| ID | Pertanyaan | Asumsi sementara (dipakai spec) | Dampak kalau berubah | Dirujuk di |
|---|---|---|---|---|
| Q-01 | Domain produksi untuk api dan web? | `karaya.app` (web) dan `api.karaya.app` (api). Sebelum domain ada, pakai `*.vercel.app`. | Hanya env `API_PUBLIC_URL`, `CORS_ORIGINS`, `accept_url`. | 02 §8, 05 §5 |
| Q-02 | Apakah preview deploy boleh menyentuh DB produksi? | Tidak. Preview api memakai DB lokal developer atau dinonaktifkan; preview web diarahkan ke api produksi hanya untuk akun tester. | Kalau boleh: tambah env per-branch. | 02 §8 |
| Q-03 | Bolehkah satu user punya lebih dari satu household? | Skema mengizinkan; API dan UI mendukung pemilih household, tetapi alur yang dijamin hanya satu household aktif. `POST /v1/households` tidak dibatasi. | Kalau dilarang: tambah unique `(user_id)` di members dan tolak `POST /v1/households` kedua. | 00 §2, 05 §4.2 |
| Q-04 | Role pasangan: `owner` setara, atau `member`? | Undangan default `role='owner'` agar suami-istri setara penuh (termasuk mengelola API key dan member). Anak/viewer diundang sebagai `member`/`viewer`. | Kalau pasangan harus `member`: hanya default undangan berubah. | 00 §3, 03 §3.3 |
| Q-05 | Visibilitas akun default dan apakah owner boleh melihat total akun privat orang lain? Apakah pengeluaran dari akun privat ikut dihitung di anggaran dan ringkasan household? | Default `shared` (`households.default_account_visibility`). Owner **tidak** bisa melihat ringkasan member lain yang punya akun privat (`403 private_scope`) kecuali setting `owners_can_view_private_totals=true` (default false). Agregat **household** menyertakan pengeluaran akun privat (anggaran keluarga adalah kesepakatan bersama) tetapi tanpa rincian, dan respons menandai `hidden_private_accounts`. | Kalau privat harus benar-benar tersembunyi dari agregat: ubah service summary/budget status untuk mengecualikan akun yang tidak `can_view`. | 03 §7.3, 05 §2.5, §3.4 |
| Q-06 | Transaksi lama berkategori "Hutang & Cicilan"/"Tabungan & Goal"/"Piutang" tidak di-link ke `debt_payments`/`goal_contributions`/`piutang_receipts`. Perlu heuristik berdasarkan `note` ("Cicilan <nama>")? | Tidak di-link; sisa lama diwakili `opening_*`. Konsekuensi: hapus transaksi cicilan lama tidak mengubah sisa hutang (sama dengan perilaku lama). | Kalau perlu: tambah skrip backfill opsional yang mencocokkan `note = 'Cicilan ' || debts.name` dan mengurangi `opening_paid` sepadan; dijalankan sekali, dicatat `migration_issues(linked_by_note)`. | 04 §2 |
| Q-07 | Apakah `merge` saat menerima undangan perlu bisa di-undo? | Tidak lewat UI. Disimpan `households.merged_into_household_id` + audit log; household sumber di-soft-delete sehingga operator bisa membalik secara manual. | Kalau perlu undo: fungsi `unmerge_household` yang memindahkan kembali semua baris berdasarkan audit log; cukup rumit, ditunda. | 05 §5 |
| Q-08 | Kalau "BCA" ambigu antara akun milik pemegang API key dan akun pasangan, bolehkah default ke milik sendiri? | Tidak (ketat, sesuai requirement). Parameter `prefer_own` ada di `resolve_account` tapi default `false`; bisa diaktifkan per API key di masa depan (`api_keys.settings.prefer_own`). | Kalau boleh: set default true untuk request API key. | 03 §8.3, 06 §4.4 |
| Q-09 | Apakah endpoint `payments`/`contributions`/`receipts` perlu menerima nama hutang/goal/piutang di body agar agent cukup satu panggilan? | Tidak; path memakai `{id}`, agent memanggil `POST /v1/resolve` dulu. Menjaga REST murni. | Kalau diperlukan: tambah `POST /v1/debt-payments` dengan `debt: "cicilan motor"` sebagai endpoint kenyamanan; registry memetakan `pay_debt` ke sana. | 05 §4.7, 06 §5 S6 |
| Q-10 | Hono vs framework lain? | Hono, sesuai keputusan. Tidak ditemukan alasan kuat untuk framework lain. Satu catatan: Vercel Hobby melarang penggunaan komersial; kalau Karaya dijual (ada halaman harga), api perlu Vercel Pro atau Cloudflare Workers (Hono mendukung keduanya tanpa perubahan kode selain adapter). | Hanya adapter dan deploy. | 00 ADR-02, 02 §8 |
| Q-11 | Apakah pg_cron tersedia dan diizinkan di project Supabase ini? | Ya (tersedia di semua plan Supabase sebagai extension yang bisa diaktifkan). | Kalau tidak: Vercel Cron (Hobby: 1 job/hari) memanggil `POST /v1/internal/run-recurrings` dengan `x-function-secret`. | 03 §10, 00 ADR-17 |
| Q-12 | **TERJAWAB (2026-10-06)**: Apakah produk ini komersial (mengaktifkan kembali subscription gating)? | **Tidak.** Pemilik produk mengonfirmasi tidak pernah ada pembayaran sungguhan. Seluruh fitur subscription/Midtrans/pricing **dihapus total** (kode, migrasi, tabel DB, edge function lama, UI `PricingModal`/`PricingSection`/`plans.js`) — bukan sekadar "dipindah" seperti asumsi lama. | Kalau nanti produk ini dikomersialkan: perlu dibangun ulang dari nol (tabel, fungsi, UI, integrasi payment gateway), bukan tinggal diaktifkan. | 00 §2, 01 §3 T5, `docs/spec/PROGRESS.md` §"Pembatalan total subscription/Midtrans" |
| Q-13 | Bolehkah AI Coach (web) menjalankan tool **tulis** (mencatat transaksi dari chat)? | Hanya bila `ai_config.allow_write = true` (default false). Saat true, UI menampilkan kartu konfirmasi sebelum tool tulis dieksekusi (dua langkah: model mengusulkan → user klik "Catat"). | Kalau selalu boleh: hapus konfirmasi. | 05 §4.12 |

## Asumsi teknis tambahan (tidak butuh keputusan produk, dicatat agar eksplisit)

- Supabase project memakai JWT asimetris (JWKS tersedia). Kalau masih HS256, `SUPABASE_JWT_SECRET` dipakai; keduanya didukung.
- Supavisor pooler transaction mode tersedia untuk project ini (standar Supabase).
- `pg_trgm`, `unaccent`, `pgcrypto` dapat diaktifkan (standar).
- Volume data per household < 100k transaksi dalam 5 tahun; semua agregasi dihitung on-the-fly tanpa materialized view.
- Hermes mampu memanggil HTTP dengan header kustom (`Idempotency-Key`) dan membaca JSON error.
- Pasangan punya email berbeda untuk akun Supabase masing-masing (satu user = satu orang).
